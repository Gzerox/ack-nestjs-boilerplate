## Goal

Extend the existing global `FeatureFlag` system with a tenant-scoped override mechanism that supports per-tenant feature behavior without changing the guard decorator API.

## What Version 1 Is

Version 1 introduces a direct per-tenant, per-flag override record.

Platform operators can set `isEnabled` and/or `config` for a specific `(tenantId, flagKey)` pair. This is the simplest delivery model and is intended as the first implementation step.

## Core Idea: Layered Resolution

Resolution evaluates from most-specific to least-specific:

```text
Priority 1 - Direct tenant override   (TenantFeatureFlagConfig)
Priority 2 - Global platform default  (FeatureFlag)
```

The `@FeatureFlagProtected('key')` decorator signature remains unchanged.

## Data Model

```prisma
model TenantFeatureFlagConfig {
  id        String    @id @default(auto()) @map("_id") @db.ObjectId

  // The tenant this override applies to.
  // Soft reference - validated at application layer.
  tenantId  String    @db.ObjectId

  // The FeatureFlag.key this override targets.
  // Soft reference - validated at application layer.
  flagKey   String

  // When null: inherit isEnable from global FeatureFlag.
  isEnabled Boolean?

  // When null: inherit metadata from global FeatureFlag.
  // When set: replaces global metadata for this tenant.
  config    Json?

  createdBy String?   @db.ObjectId
  updatedBy String?   @db.ObjectId
  createdAt DateTime  @default(now())
  updatedAt DateTime  @updatedAt

  // One override per (tenant, flag).
  @@unique([tenantId, flagKey])

  @@index([tenantId, flagKey])
  @@index([tenantId])
  @@index([flagKey])

  @@map("TenantFeatureFlagConfigs")
}
```

## Config Schema Contract

`FeatureFlag.metadata` and `TenantFeatureFlagConfig.config` should be treated as **runtime values**, not as the source of truth for config shape.

The source of truth for shape should live in code, per `FeatureFlag.key`, for example through a schema registry:

```text
FeatureFlag.key -> schema + defaults + validation rules
```

Why this matters:

- if code starts reading `aiAssistant.newConfig`
- but the persisted `FeatureFlag.metadata` document was never updated
- a pure runtime lookup can fail only when that path is accessed in production

Recommended contract:

1. Code defines the allowed config shape for each flag.
2. Code defines defaults for newly introduced properties.
3. Persisted `metadata` and tenant `config` only override those defaults.
4. On read, the effective config is built as:
   - code defaults
   - overridden by global `FeatureFlag.metadata`
   - overridden by tenant `TenantFeatureFlagConfig.config`
5. Unknown keys should be rejected on write.
6. Missing required keys should be detected before runtime, through validation at startup, admin write-time validation, or CI checks.

Practical effect for your scenario:

- adding a new property in code should not require every DB row to be updated immediately
- if the property has a safe default in code, old DB documents continue to work
- if the property is required and has no safe default, startup or admin validation should fail loudly instead of allowing a latent runtime failure

Recommended fail behavior:

- for boolean gate checks, missing path should evaluate to disabled
- for config reads, missing required values should throw a controlled configuration error, not an untyped runtime error
- for admin writes, payloads should be validated against the code-defined schema for that flag

## Resolution Algorithm

```text
resolveFlag(flagKey, tenantId?, userId?):

  1. Load global FeatureFlag by flagKey (cache: FeatureFlag:{flagKey}).
     If not found -> throw NotFoundException.

  2. If tenantId exists:
       Load TenantFeatureFlagConfig by (tenantId, flagKey)
       (cache: FeatureFlag:{flagKey}:Tenant:{tenantId}).

  3. Compute effective state:
       effectiveIsEnabled = override?.isEnabled ?? global.isEnable
       effectiveConfig    = override?.config    ?? global.metadata

  4. If effectiveIsEnabled = false -> throw ServiceUnavailableException (503).

  5. If keyPath has metadata segment:
       Read effectiveConfig[metadataKey].
       If not boolean or not true -> throw ServiceUnavailableException (503).

  6. Rollout check:
       - If a direct tenant override exists: skip rollout.
       - Else if userId present and global.rolloutPercent < 100:
           compute deterministic bucket and enforce rollout.
```

## Cache Strategy

Use only 2 cache keys in this version:

| Cache Key | Content | TTL | Invalidated When |
|---|---|---|---|
| `FeatureFlag:{flagKey}` | Global `FeatureFlag` record | 1h | Global flag updated |
| `FeatureFlag:{flagKey}:Tenant:{tenantId}` | `TenantFeatureFlagConfig` record or null sentinel | 1h | Override upserted or deleted |

## Admin API

All endpoints require platform operator role.

| Method | Path | Description |
|---|---|---|
| `GET` | `/admin/tenants/:tenantId/feature-flags` | List all overrides for a tenant |
| `PUT` | `/admin/tenants/:tenantId/feature-flags/:flagKey` | Upsert override |
| `DELETE` | `/admin/tenants/:tenantId/feature-flags/:flagKey` | Remove override and revert to global |

`PUT` validation rules:

1. `flagKey` must exist in `FeatureFlag`.
2. `tenantId` must reference an existing tenant.
3. If `config` is provided, keys must be compatible with the global metadata schema.

## Acceptance Criteria

1. `TenantFeatureFlagConfig` CRUD works with uniqueness by `(tenantId, flagKey)`.
2. Resolution applies direct tenant override when present.
3. Resolution falls back to global flag when override is absent.
4. Rollout check is skipped when direct tenant override exists.
5. Cache invalidates on every write to `TenantFeatureFlagConfig`.
6. `@FeatureFlagProtected` decorator and guard API remain unchanged.
7. Admin endpoints exist:
   - `GET /admin/tenants/:tenantId/feature-flags`
   - `PUT /admin/tenants/:tenantId/feature-flags/:flagKey`
   - `DELETE /admin/tenants/:tenantId/feature-flags/:flagKey`
8. Feature flag config writes are validated against a code-defined schema per `flagKey`.
9. Newly added config properties can be introduced safely through code defaults without requiring immediate DB backfill.

## Current Limitations

1. One active direct override per `(tenantId, flagKey)`.
2. No tenant self-serve.
3. No per-user or per-project scoping in v1.
4. No reusable preset bundles.
5. No audit event history stream yet.

## Relationship to Version 2

Version 1 remains useful even after v2 exists.

In the future stack:

- v1 direct override stays the highest-priority tenant exception layer
- v2 preset becomes the reusable shared-default layer below it
