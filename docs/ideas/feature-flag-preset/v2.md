## Goal

Introduce reusable preset bundles for assigning the same flag package to many tenants, while preserving the direct tenant override model from v1 and keeping the guard decorator API unchanged.

## What Version 2 Achieves

Version 2 introduces a reusable feature package that can be assigned to many tenants without writing the same per-tenant override rows repeatedly.

It solves the operational problem that appears once the same flag combination must be reused across multiple tenants:

- in v1, enabling the same set of flags for 20 tenants means writing and maintaining 20 independent groups of `TenantFeatureFlagConfig` rows
- in v2, that same set of flag decisions is defined once in a `FeatureFlagPreset`, then linked to many tenants through `TenantFeatureFlagPreset`

This gives us:

1. Reuse: define a named rollout package once.
2. Consistency: all assigned tenants resolve the same flag values.
3. Lower operational cost: changes to the preset can affect all assigned tenants without editing each tenant separately.
4. Clear intent: operators can reason in business terms such as `beta-partners` or `enterprise-defaults`.

## Difference From Version 1

| Area | Version 1 | Version 2 |
|---|---|---|
| Main concept | Direct override per `(tenantId, flagKey)` | Reusable named preset assigned to one or more tenants |
| Best for | One-off tenant customization | Repeated bundles shared across many tenants |
| Write pattern | Many rows copied across tenants | Define once, assign many |
| Change propagation | Update each tenant override separately | Update preset once, all assigned tenants inherit it |
| Operational intent | Tenant-specific exception | Segment-level shared package |
| Resolution layer | Tenant override -> global flag | Tenant override -> tenant preset -> global flag |

Reference: [Version 1 Spec](v1.md)

## Scope

Version 2 is not a replacement for v1. It adds an extra middle layer:

- global `FeatureFlag` remains the platform baseline
- `FeatureFlagPreset` becomes the shared tenant segment default
- `TenantFeatureFlagConfig` remains the tenant-specific exception layer

## Proposed Data Model

```prisma
model FeatureFlagPreset {
  id            String   @id @default(auto()) @map("_id") @db.ObjectId

  // Stable identifier used in APIs and cache keys.
  key           String   @unique
  name          String
  description   String?
  isActive      Boolean  @default(true)

  // Map keyed by FeatureFlag.key.
  // Each entry follows the same semantics as TenantFeatureFlagConfig.
  config        Json

  createdBy     String?  @db.ObjectId
  updatedBy     String?  @db.ObjectId
  createdAt     DateTime @default(now())
  updatedAt     DateTime @updatedAt

  @@index([key])
  @@index([isActive])
  @@map("FeatureFlagPresets")
}

model TenantFeatureFlagPreset {
  id         String   @id @default(auto()) @map("_id") @db.ObjectId

  // Soft reference - validated at application layer.
  tenantId   String   @db.ObjectId

  // Soft reference to FeatureFlagPreset.key
  presetKey  String
  isActive   Boolean  @default(true)

  createdBy  String?  @db.ObjectId
  updatedBy  String?  @db.ObjectId
  createdAt  DateTime @default(now())
  updatedAt  DateTime @updatedAt

  @@unique([tenantId, presetKey])
  @@index([tenantId])
  @@index([presetKey])
  @@index([tenantId, isActive])
  @@map("TenantFeatureFlagPresets")
}
```

For the initial v2 implementation, application-level validation should enforce at most one active preset per tenant, even if the persistence model remains flexible for later evolution.

## Config Schema Contract

Version 2 should follow the same schema ownership model as v1:

- code owns the config shape per `FeatureFlag.key`
- database documents store only values and overrides
- missing newly introduced properties should resolve through code defaults, not through implicit runtime assumptions

The effective config should therefore be built in layers:

1. code defaults for the flag
2. global `FeatureFlag.metadata`
3. preset entry `FeatureFlagPreset.config[flagKey].config`
4. direct tenant override `TenantFeatureFlagConfig.config`

This prevents the common failure mode where code starts reading a new nested property but old DB documents do not contain it yet.

## Preset Shape

The preset stores a `config` object keyed by `FeatureFlag.key`. Each entry follows the same semantics as `TenantFeatureFlagConfig`:

- `isEnabled: null | boolean`
- `config: null | json`

Example:

```json
{
  "aiAssistant": {
    "isEnabled": true,
    "config": {
      "chat": true,
      "summaries": true
    }
  },
  "changePassword": {
    "isEnabled": true,
    "config": {
      "forgotAllowed": true
    }
  },
  "advancedBilling": {
    "isEnabled": false,
    "config": null
  }
}
```

## How It Would Be Used

Typical workflow:

1. Create a preset such as `beta-partners`.
2. Put the desired shared flag package into `config`.
3. Assign that preset to multiple tenants.
4. If one tenant needs an exception, add a direct `TenantFeatureFlagConfig` row for only that tenant and flag.

This gives a clean operating model:

- global `FeatureFlag` = platform baseline
- `FeatureFlagPreset` = shared tenant segment default
- `TenantFeatureFlagConfig` = tenant-specific exception

## Resolution Algorithm

```text
resolveFlag(flagKey, tenantId?, userId?):

  1. Load global FeatureFlag by flagKey (cache: FeatureFlag:{flagKey}).
     If not found -> throw NotFoundException.

  2. If tenantId exists:
       Load TenantFeatureFlagConfig by (tenantId, flagKey)
       (cache: FeatureFlag:{flagKey}:Tenant:{tenantId}).

  3. If direct tenant override exists:
       effectiveIsEnabled = override.isEnabled ?? global.isEnable
       effectiveConfig    = override.config    ?? global.metadata
       source             = "tenant-override"
       skip preset lookup

  4. Else if tenantId exists:
       Load active preset assignment(s) for tenantId
       (cache: TenantPresets:Tenant:{tenantId}).

  5. If an active preset contains flagKey:
       Load preset document(s) as needed
       (cache: Preset:{presetKey}).
       presetEntry        = preset.config[flagKey]
       effectiveIsEnabled = presetEntry.isEnabled ?? global.isEnable
       effectiveConfig    = presetEntry.config    ?? global.metadata
       source             = "preset"

  6. Else:
       effectiveIsEnabled = global.isEnable
       effectiveConfig    = global.metadata
       source             = "global"

  7. If effectiveIsEnabled = false -> throw ServiceUnavailableException (503).

  8. If keyPath has metadata segment:
       Read effectiveConfig[metadataKey].
       If not boolean or not true -> throw ServiceUnavailableException (503).

  9. Rollout check:
       - If source = "tenant-override" or source = "preset": skip rollout.
       - Else if userId present and global.rolloutPercent < 100:
           compute deterministic bucket and enforce rollout.
```

## Precedence Rules

The default precedence should be:

1. `TenantFeatureFlagConfig`
2. `FeatureFlagPreset`
3. `FeatureFlag`

That means:

- direct tenant override always wins over preset
- preset wins over global default
- rollout only applies when resolution falls back to global

## Preset Assignment Strategy

The safest first implementation is one active preset per tenant.

Why start there:

- no preset-to-preset conflict resolution
- no merge-order ambiguity
- cache behavior stays simple
- operators can still use direct tenant overrides for exceptions

If multiple presets per tenant are added later, the system must define:

- merge order
- conflict handling when two presets define the same `flagKey`
- whether last-assigned-wins is acceptable or too implicit

## Acceptance Criteria

1. Preset catalog and assignment are introduced without breaking v1 behavior.
2. The same preset can be assigned to multiple tenants without duplicating per-tenant flag rows.
3. Direct tenant overrides continue to take precedence over presets.
4. Preset-specific cache keys are introduced only when preset resolution is implemented.
5. Resolution remains deterministic: tenant override -> preset -> global.
6. Preset config entries are validated against the same code-defined schema contract used by v1.

## Future Extensions

1. Tenant assignment UI and admin APIs for preset lifecycle management.
2. Scheduled preset assignment or expiration windows.
3. Per-project or per-user resolution layers above tenant.
4. Instant cache invalidation via pub/sub.
5. Append-only audit log for override and assignment history.
6. Preset precedence strategy for intentional overlap.
